  2. Architecture

  Browser UI (static HTML/JS)  ─┐
  REST clients ─────────────────┤→ FastAPI
                                │    ├─ Ingestion: parse → normalize → chunk →
  embed → index
                                │    ├─ Query: retrieve (hybrid) → threshold →
  prompt → LLM → validate citations
                                │    └─ Providers: Embedder / ChatModel
  interfaces (OpenAI | Fake)
                                └→ Local storage: data/<collection>/ (SQLite
  metadata + vectors + BM25)

  Planned endpoints: POST/GET/DELETE /collections, POST
  /collections/{id}/documents (multipart), GET/DELETE .../documents/{doc_id},
  POST /collections/{id}/query → {answer, answerable, citations[{doc,
  page/section, chunk_id, snippet, score}]}, GET /health.

  Main trade-offs

  Chunking
  - Fixed-size token windows: simple, but they cut through sentences and
    sections.
  - Structure-aware recursive splitting (recommended): split on headings, then
    paragraphs, then sentences. Target about 500–800 tokens with about 15%
    overlap, measured with tiktoken. Each chunk keeps doc_name, page,
    heading_path and chunk_index. This gives better citations and more coherent
    context.
  - Semantic chunking (embedding-based splits): higher ingest cost and hard to
    test deterministically. I'd skip it.

  Retrieval
  - Dense only (cosine over OpenAI embeddings): good on meaning, weak on exact
    terms such as IDs, names and acronyms.
  - Hybrid dense + BM25, merged with Reciprocal Rank Fusion (recommended):
    robust across different kinds of documents, which matters because the brief
    requires it to work on any document set. It costs one small dependency
    (rank-bm25).
  - Adding an LLM or cross-encoder reranker: better precision, but more latency,
    cost and dependencies. I'd leave it as an optional later step.

  Storage

  Option: SQLite + NumPy vectors (recommended)
  Pros: No server, a few dependencies, fully transparent, trivial to test,
  brute-force search is fast up to ~100k chunks
  Cons: You write the search yourself (about 30 lines)
  ────────────────────────────────────────
  Option: ChromaDB (embedded)
  Pros: Ready-made persistence and filtering
  Cons: Heavier install (issues on Windows are common), less control, harder to
  fake in tests
  ────────────────────────────────────────
  Option: FAISS / LanceDB
  Pros: Scales further
  Cons: More than this assessment needs

  Keeping answers grounded (layered, because no single mechanism is enough)
  1. Retrieval gate: if the best fused or cosine score is below a threshold,
     return "not in documents" without calling the LLM. This is cheap and hard
     to game.
  2. Constrained prompt: passages numbered [S1]…[Sn] with their source metadata.
     Instructions: answer only from the sources, cite every claim, and output a
     fixed not-found token if the sources don't cover the question.
     Temperature 0.
  3. Structured output: JSON schema {answerable, answer, cited_sources[]}
     through OpenAI's structured outputs, so the result can be parsed reliably.
  4. Post-validation: remove citations that point to sources that weren't
     retrieved. If an "answerable" response has no valid citations, downgrade it
     to not-found.
  5. Transparency: the UI shows the cited passages next to the answer.

  Other design points
  - Duplicate uploads are detected by content hash.
  - Each collection records its embedding model, so a later model change is
    caught and the collection can be re-indexed.
  - Upload size limit and file-type checks.
  - Ingestion runs in the request for simplicity. Background jobs are possible
    but add complexity.

  UI: a single static index.html with vanilla JS, served by FastAPI. There's no
  build step and no Node, and it's one process on one port. Streamlit is the
  alternative, but it would need a second process and wouldn't use the REST API
  as naturally.

  Libraries: fastapi, uvicorn, python-multipart, pydantic-settings, openai,
  pypdf, python-docx, tiktoken, numpy, rank-bm25, pytest, httpx.
